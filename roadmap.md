# Roadmap / продуктовые идеи

В отличие от `todo.md` (технический долг — код, DTO, тесты), здесь — наблюдения по
**бизнес-смыслу и логике самой симуляции**: что реализовано, но недоступно из UI, чего не
хватает в модели Kanban-потока, и что усилило бы инструмент как обучающий/исследовательский.
Ничего из этого не решено к реализации — это материал для обсуждения перед тем, как трогать
код.

## Готово в движке, но недоступно из UI

- **`RequiresDifferentResource`/`RequiresDifferentResourceFromStage`** — принцип «код-ревью
  должен делать не тот, кто писал код» (four-eyes principle). Полностью реализован в
  `TaskMovementService` (реально блокирует назначение того же воркера — см. проверку в методе
  `FindAvailableWorker`), поле есть в DTO и мапперах. Но в редакторе стадий
  (`config-editor.js` → `renderStages()`) нет ни одного поля для него, и ни один пресет его не
  использует — включить можно только руками через импорт JSON. Решить: либо доделать один
  select в форме стадии, либо выпилить как мёртвый вес из DTO.
- **`ApiTaskDto.Children`** (иерархические задачи/подзадачи) — есть в DTO и в домене, ноль UI,
  ноль примеров в пресетах. Потенциально — эпики со стори.
- **`ApiTaskDto.AcceptableWorkers`** (закрепить конкретного воркера за конкретной стадией для
  конкретной задачи, «этот PR может смержить только Аня») — есть в DTO, ноль UI.

Общий паттерн: движок в какой-то момент ушёл вперёд UI, и три фичи осели мёртвым весом. По
каждой стоит решить: доделать редактор или убрать из DTO, чтобы не путать.

## Чего нет в самой модели симуляции

- **Нет непрерывного прихода задач.** Все задачи существуют с дня 0 фиксированным пакетом —
  по сути это симуляция burn-down (как в Scrum-спринте), а не потока (как в реальном Kanban).
  Ключевая ценность Kanban — работа с *переменным* потоком поступления в сравнении с
  пропускной способностью (закон Литтла, что происходит, когда приход приближается к ёмкости
  команды или обгоняет её). Сейчас это в принципе нельзя показать: нет ни ставки прихода
  задач, ни очереди, которая растёт из-за того, что приход обогнал throughput. Для инструмента
  под названием "KanbanFlow Simulation" это довольно центральный пробел, не косметика.
- **Нет класса обслуживания / expedite.** В реальном Kanban почти всегда есть приоритетные
  полосы (standard / fixed-date / expedite) — это то, что определяет, какая задача возьмётся
  раньше при конкуренции за одного воркера. Сейчас порядок — просто порядок в списке задач,
  пользователь не может сказать "эта задача горит, возьми первой".
- **Нет понятия "заблокировано".** Buffer/Work — это состояние процесса, а не состояние
  конкретной карточки. В реальности задача может физически "зависнуть" на любой стадии (ждём
  внешнюю команду, ждём решение) — сейчас это неотличимо от нормального ожидания в очереди, а
  "время блокировки" — одна из стандартных Kanban-метрик, которой тут неоткуда взяться.

## С точки зрения обучающего инструмента (метрики/UX)

- **Нет режима сравнения сценариев.** Весь смысл такого симулятора — "покрути WIP-лимит и
  посмотри, что будет с Lead Time" — но сейчас можно смотреть только один прогон за раз, без
  A/B рядом. Вся конфигурация уже лежит в JSON и легко клонируется — side-by-side сравнение
  двух прогонов (например, WIP=2 vs WIP=4 на одном и том же наборе задач) кажется естественным
  следующим шагом и, вероятно, самым дешёвым по эффекту пунктом из всего списка.
- **Закон Литтла нигде не показан явно**, хотя все три величины (WIP, Throughput, Lead Time)
  уже считаются по отдельности — свести их в одну карточку "WIP = Throughput × Lead Time" было
  бы дешёвым и наглядным дополнением именно для обучения.
- **Нельзя отмотать назад.** История по дням хранится полностью (`RandomCallCount` + `History`
  в `ApiSimulationStateDto`), то есть технически можно реконструировать состояние на любой
  прошлый день — но UI даёт только идти вперёд, "перемотки" к дню N нет. Для исследовательского
  инструмента ("а что было на 5-й день, когда затор начался") это заметный пробел при том, что
  данные для него уже есть.

## Осознанно не берём

- **Календарь/отсутствия воркеров** (выходные, отпуска) — обсудили, решили не делать: для
  целей инструмента практического смысла не даёт, а сложности (календарные vs рабочие дни
  всюду в метриках, UI для отпусков) добавляет ощутимо.
