# Обучающие сценарии — дизайн

Материал для тренинга: несколько команд получают один и тот же — намеренно кривой,
несбалансированный — конфиг и должны его оптимизировать. Единственный жёсткий инвариант:
**общая длительность задач по каждому навыку** (backend/frontend/qa) не меняется. Всё
остальное — состав команды, WIP-лимиты, дробление/слияние задач, даже структура workflow —
можно менять свободно.

Реализовано как 4 JSON-файла в `training-scenarios/` (импортируются через UI кнопкой
«Импорт», ничего в коде/пресетах не трогают) + `training-scenarios/README.md` — памятка
фасилитатору с базовыми цифрами. Все цифры ниже по каждому уровню — не оценка на бумаге, а
**реально измеренные** через `POST /api/simulation/start` + `/all-metrics` на этих самых
файлах (seed=42, `useVariability: true`), см. раздел проверки в конце. См. также [[roadmap]]
(продуктовые пробелы движка) и `json-model.md` (форма JSON).

## Механика движка, важная для калибровки сценариев

Прежде чем считать конкретные цифры, три вещи, которые нашлись в коде и напрямую влияют на то,
как «выстрелит» сценарий:

1. **Длительность считается отдельно на каждой Work-стадии**, не одним числом на задачу:
   `ceil(shirtDays × stageProgressPercent / 100)` — `StageExtensions.GetDaysForTask`. У задачи,
   проходящей через 5 Work-стадий с процентами 25/100/50/30/10, длительность на каждой стадии
   считается по отдельности и суммируется — сумма процентов может быть больше 100% (это нормально,
   так уже устроены существующие пресеты, напр. `kanban-software`: 100+30+10=140%).
2. **У каждой Work-стадии есть пол в 1 день** (`WorkerExtensions.GetDaysForTask`:
   `Math.Max(1, ceil(...))`), независимо от размера задачи. Из этого следует **налог на
   дробление**: чем длиннее пайплайн (больше Work-стадий, которые задача обязана пройти), тем
   дороже становится каждая мелкая задача просто за счёт округления вверх на каждой стадии —
   см. точный расчёт в [Уровне 4](#уровень-4-плохая-декомпозиция-vs-налог-на-дробление).
3. **Многозадачность воркера не имеет искусственного штрафа за переключение.** Если у воркера
   `wipLimit > 1` и несколько активных задач, он делит день `1 / N` между ними
   (`WorkProgressService.SimulateWorkDay`, `share = 1.0m / activeWorkCount`) — сумма
   отработанного размазывается честно, штрафа сверху нет. «Вред» от чрезмерного WIP в этом
   движке — чисто в Lead Time (задачи финишируют одновременно и поздно), а не в потере
   суммарной производительности — это важно проговорить на тренинге как честное упрощение
   модели.

### Гоча с `Task.RequiredSkills` — важно при сборке JSON

`CanTaskMoveToStage` пускает задачу на стадию, только если у задачи и у стадии есть **общий**
навык (или у одной из сторон список навыков пуст). Если у задачи `requiredSkills: ["backend"]`,
а дальше по пайплайну есть стадия с `requiredSkills: ["qa"]` — задача **не сможет войти на эту
стадию никогда** и зависнет в предыдущем буфере навечно (тихий deadlock, в UI выглядит как
задача, которая просто перестала двигаться).

Правило при сборке сценариев с несколькими разноскиловыми Work-стадиями подряд (Level 2, 3, 4):
**у задач `requiredSkills` должен быть пустым** (`[]`) — гейтинг по навыкам делает стадия, а не
задача. `requiredSkills` на задаче стоит использовать только там, где это часть замысла — жёстко
запереть задачу на одну ветку/один навык (пригодится как отдельный сценарий про «рельсы» и
голодание, см. бэклог идей в конце).

## Общий формат уровня

Для каждого уровня: workflow, состав команды, список задач, ожидаемый симптом на первом
прогоне (что команда увидит на доске/в метриках), ожидаемое направление фикса и концепция
Kanban/TOC, которую он вскрывает.

Размеры задач (реальный enum, `TShirtType.cs` — не путать с устаревшим README):
`XS=1, S=2-3 (mid 2.5), M=4-6 (mid 5), L=7-15 (mid 11)` дней на 100%-стадии.

## Уровень 1: Один явный затор + бесполезный хедкаунт

**Workflow** (4 стадии, один Work): `Backlog(Buffer) → Todo(Buffer, isLeadTimeStart, wip=5) →
Developing(Work, 100%, skills=[backend]) → Done(Buffer)`.

**Команда** (3 человека, но полезен один):
- `dev-be`: skills=[backend], wip=1, performance=100
- `dev-fe`: skills=[frontend], wip=1, performance=100 — **в этом workflow нет ни одной стадии,
  которую он может делать**
- `qa`: skills=[qa], wip=1, performance=100 — аналогично, простаивает 100% времени

**Задачи**: 8 шт., все `requiredSkills=[]` (см. гочу выше — не обязательно для одностадийного
процесса, но привычка правильная), размеры: 2×L, 3×M, 3×S. В заголовках стоит префикс `[BE]` —
в этом workflow вся работа бэкендная, тег нужен чтобы на доске сразу было видно: ни одной
`[FE]`-карточки нет, а в команде сидят `dev-fe` и `qa`. Суммарно по backend-навыку ≈
2×11 + 3×5 + 3×2.5 = 44.5 номинальных дня.

**Симптом на первом прогоне**: `dev-be` работает без остановки весь прогон, `dev-fe`/`qa`
в WorkerMetrics показывают `efficiencyPercent ≈ 0` всю дорогу. Три человека в команде — а
бутылочное горлышко работает в одиночку.

**Измерено на `level-1-single-bottleneck.json`**: симуляция завершается на 49-й день;
`dev-be.efficiencyPercent = 100`, `dev-fe.efficiencyPercent = 0`,
`qa.efficiencyPercent = 0` (буквально ноль, не «близко к нулю»); `leadTime.p50 = 29.5`,
`p85 = 38.7`; `flowEfficiency ≈ 17.75%` (низкая — задачи подолгу ждут своей очереди к
единственному занятому человеку); `totalCost = 14700` (3 воркера × 100/день × 49 дней).

**Что должна поправить команда**:
- Минимальный фикс: сменить/добавить `dev-fe`/`qa` навык `backend` — сразу утраивает
  capacity на единственной Work-стадии.
- Более зрелый фикс: перепроектировать workflow так, чтобы под frontend/qa реально появилась
  работа (это уже шаг в сторону Level 2 — стоит явно проговорить на дебрифе, что это тоже
  валидный путь, просто дороже).

**Урок**: первый фокусирующий шаг ТОС — **найти ограничение**, а не считать головы. «3 человека
в команде» ничего не говорит о capacity, если 2 из 3 не могут физически взять работу со стадии.

## Уровень 2: Избыточное QA

**Workflow**: копия `kanban-software` (8 стадий) — `Planning → Todo(wip=5, isLeadTimeStart) →
Developing(100%, skills=[backend,frontend]) → Ready for Testing → Testing(30%, skills=[qa]) →
Ready to Merge → Release Prep(10%, skills=[backend,frontend]) → Done`.

**Команда** (5 человек, перекос в QA):
- `dev1`: skills=[backend,frontend], wip=1, performance=100 — единственный, кто может двигать
  Developing/Release Prep
- `qa1..qa4`: skills=[qa], wip=1, performance=100 — четверо на одну лёгкую (30%) стадию

**Задачи**: 10 шт., `requiredSkills=[]` **обязательно** (гейтинг только по стадии, иначе задача
не дойдёт из Developing до Testing — см. гочу выше). Размеры: 4×S, 4×M, 2×L.

**Симптом**: `dev1` — сериализованный бутылочный узел на Developing, `qa1..qa4` в метриках
почти всё время `efficiencyPercent` близко к нулю — реальной работы на Testing (30%-стадия)
на четверых кратно меньше, чем они могут переварить. На CFD — Developing явно самая толстая
полоса, Testing почти не растёт.

**Измерено на `level-2-excess-qa.json`**: завершение на 74-й день;
`dev1.efficiencyPercent = 97.3`; из четырёх QA только `qa1` вообще что-то делает
(`efficiencyPercent = 51.4`) — **`qa2`, `qa3`, `qa4` весь прогон на нуле**, ни одной задачи;
`leadTime.p50 = 34.5`, `p85 = 52.9`; `flowEfficiency ≈ 25.5%`; `totalCost = 37000` — почти в
2.5 раза больше, чем в Level 1, при сопоставимом объёме задач, потому что три из пяти
зарплат идут в буфер простоя. `totalCost` тут — отдельный, наглядный аргумент против «на
всякий случай наймём QA с запасом».

**Что должна поправить команда**: перебросить часть QA в backend/frontend (кросс-скиллинг —
изменить состав, что разрешено правилами), либо честно сократить QA-часть команды и
перераспределить бюджет на dev. Ключевая мысль: не «нужно больше QA чтобы не было бага в
процессе», а «мощность должна быть там, где реальный спрос».

**Урок**: балансировка мощности **под спрос по стадиям**, а не под интуицию «QA всегда мало» —
здесь ровно наоборот, QA явно избыточен.

## Уровень 3: WIP-хаос — «начать всё, не закончить ничего»

**Workflow**: тот же `kanban-software`-подобный процесс, но **без стадийных WIP-лимитов** нигде
(`wipLimit: null` везде, включая Todo).

**Команда** (сбалансированная по скиллам — сознательно не в этом проблема):
- `dev1`, `dev2`: skills=[backend,frontend], performance=100, но **wip=6** (не 1!)
- `qa1`: skills=[qa], performance=100, wip=6

**Задачи**: 10 шт. того же состава, что и в Level 2 (4×S, 4×M, 2×L), `requiredSkills=[]`.

**Симптом**: без стадийных WIP-лимитов все 10 задач залетают в Developing одновременно (нечему
их придержать), у `dev1`/`dev2` тут же по несколько активных назначений каждый — прогресс
размазывается `1/N` в день на каждую. Результат: почти ничего не завершается **очень долго**,
потом всё финиширует одним большим комком в конце — при том, что суммарный объём выполненной
работы (worker-days) тот же самый, что и при последовательной обработке.

**Измерено на `level-3-wip-chaos.json`**: завершение на 47-й день; `leadTime.p50 = 35.0`,
`p85 = 40.3`; `throughput.overall ≈ 0.213`; `totalCost = 14100`.

**Важная методическая ловушка, найденная при проверке (а не предсказанная заранее)**:
`flowEfficiency` в этом прогоне — **99.4%**, выглядит идеально. Это не ошибка сценария, а
особенность метрики: `flowEfficiency = active / (active + wait)`, а `wait` считается только
как время в Buffer-стадиях. Без стадийных WIP-лимитов задачам физически негде ждать в буфере —
они мгновенно улетают в Work-стадию, поэтому «wait» почти нулевой и метрика выглядит отлично,
хотя каждая отдельная задача еле ползёт из-за размазывания `1/N`. Проверка того же бэклога с
`wipLimit=1` у воркеров и вменяемыми стадийными лимитами (Todo=5, Developing=3, Testing=2)
дала: `leadTime.p50 = 20.5` (−41%), `p85 = 28.6` (−29%), `throughput.overall ≈ 0.217`
(практически не изменился) — а `flowEfficiency` при этом **упал до 41.4%**, потому что теперь
задачи честно видно ждущими в буфере перед тесными WIP-стадиями.

Это стоит явно проговорить на дебрифе как отдельный урок: **`flowEfficiency` в этом движке не
детектирует вред от многозадачности воркера** — она реагирует только на буферное ожидание, и
может выглядеть «хорошо» ровно в момент, когда WIP-хаос максимален. Сигнал, которому здесь
можно доверять — `leadTime.p50/p85` при стабильном `throughput`, не `flowEfficiency`.

**Что должна поправить команда**: снизить `wipLimit` воркеров до 1 и/или выставить осмысленные
стадийные WIP-лимиты (под реальную capacity команды) — Lead Time падает в разы при том же
throughput. Явный побочный урок: если команда после фикса посмотрит только на
`flowEfficiency` и увидит, что он «стал хуже», — это ложный сигнал отката назад, важно
сверяться с `leadTime`.

**Урок**: закон Литтла (`WIP = Throughput × Lead Time`) на живых цифрах — тот же throughput,
кардинально разный Lead Time в зависимости от WIP. Плюс критическое мышление про метрики: одна
цифра из дашборда не заменяет понимания, что она на самом деле измеряет.

## Уровень 4: Плохая декомпозиция vs налог на дробление

Открытый эксперимент, а не сценарий с одним «правильным» ответом — специально задуман так,
чтобы решение могло пойти в любую сторону в зависимости от того, что команда сделает с WIP и
составом одновременно с дроблением.

**Workflow** (5 Work-стадий, сокращённая версия `twork-process`): `Planning(Buffer) →
Todo(Buffer, wip=6, isLeadTimeStart) → Tech Spec(Work, 25%, skills=[backend]) →
Developing(Work, 100%, wip=3, skills=[backend,frontend]) → Code Review(Work, 50%, wip=2,
skills=[backend]) → Testing(Work, 30%, wip=2, skills=[qa]) → Ready to Release(Work, 10%,
skills=[backend,frontend]) → Done(Buffer)`.

**Команда**: 2×backend (wip=1), 1×frontend (wip=1), 1×qa (wip=1), все performance=100.

**Задачи (вариант «как есть»)**: 4×L, `requiredSkills=[]`. Подпись в описании задачи:
«эпик плохо разбит, тестировщики жалуются, что тестируют кусками по 15 дней».

**Точный расчёт (mid-оценка, без вариативности, `performance=100`) — уже проверен по формуле
движка**:

| | Tech Spec 25% | Developing 100% | Code Review 50% | Testing 30% | Release 10% | Итого |
|---|---|---|---|---|---|---|
| 1×L (mid 11) | 3 | 11 | 6 | 4 | 2 | **26 дней** |
| 4×S (mid 2.5 каждая) | 1×4=4 | 3×4=12 | 2×4=8 | 1×4=4 | 1×4=4 | **32 дня** |

Дробление одной L на 4×S даёт **+23% суммарной работы** по чистой mid-оценке (32 против 26
worker-days) — эффект округления вверх на каждой из 5 стадий, без всякого «переключения». Это
не баг сценария, а прямое следствие формулы `Math.Max(1, ceil(...))`, действующей на каждой
Work-стадии отдельно. С учётом вариативности (`deviationDownPercent`/`deviationUpPercent` у
воркеров — тоже случайный множитель поверх ceiling-эффекта) реальный налог на практике оказался
ещё выше — см. измерения ниже.

**Измерено на `level-4-decomposition-tax.json` («как есть», 4×L)**: завершение на 51-й день;
`leadTime.p50 = 37.0`, `p85 = 47.75`; `flowEfficiency ≈ 69.8%`; `totalCost = 20400`;
суммарно отработано **112 worker-days**. По воркерам явно видно, кто на критическом пути:
`be-dev-1.efficiencyPercent = 98.0`, `be-dev-2 = 76.5`, `qa-eng-1 = 37.3`, а
`fe-dev-1 = 7.8` — фронтендер в этом workflow почти не нужен (Developing уже насыщен
WIP-лимитом=3 и двумя backend-воркерами раньше, чем до него доходит очередь).

**Три прогона с раздробленным бэклогом (16×S вместо 4×L, тот же состав по навыкам)** —
дают ровно ту неоднозначную картину, ради которой сценарий задуман:

| Вариант | День завершения | Lead Time p50 / p85 | Throughput | `totalCost` | Суммарно worker-days |
|---|---|---|---|---|---|
| Как есть (4×L) | 51 | 37.0 / 47.75 | 0.078 | 20400 | 112 |
| Просто дробим (16×S, WIP/состав не трогаем) | **65** (хуже!) | **29.0 / 33.75** (лучше!) | 0.246 | 26000 (+27%) | 182 (+62%) |
| Дробим + поднимаем WIP на Dev/CR/Testing | 65 (без изменений) | 29.0 / 33.75 (без изменений) | 0.246 | 26000 | 182 |
| Дробим + WIP + **ещё один backend-воркер** | **46** (лучше исходного) | **22.0 / 27.75** | 0.348 | 23000 (+13%) | — |

Прочитать стоит внимательно, тут две отдельные находки:
- **Простое дробление без добавления людей уже улучшает медианный/p85 Lead Time** (37→29,
  47.75→33.75) — отдельные задачи долетают быстрее. Но общий срок закрытия всего бэклога
  (`currentDay`) при этом **вырос** (51→65) — потому что суммарного объёма работы стало на 62%
  больше, а число людей то же самое. Это ровно та развилка «средний срок одной задачи против
  срока всего бэклога», которую стоит явно обсудить на дебрифе — команда, которая смотрит
  только на `leadTime.p50`, увидит успех; та, что смотрит на дату сдачи всего скоупа, увидит
  провал.
- **Поднятие стадийных WIP-лимитов (Dev/Code Review/Testing) без изменения состава команды не
  дало вообще никакого эффекта** — числа идентичны варианту без этого шага. Причина: реальное
  ограничение — не стадийный WIP, а `wipLimit=1` у каждого из 4 воркеров (только 2 backend).
  Добавление одного backend-воркера (5-й человек) — и только тогда — дало честный выигрыш и по
  Lead Time, и по сроку всего бэклога, при разумных +13% к стоимости. Хорошая живая иллюстрация
  того, что крутить видимый рычаг (WIP-лимит стадии) бессмысленно, если ограничение сидит на
  уровне ниже (в данном случае — capacity конкретных людей).

Дебрифу стоит явно вывести это как компромисс **Lead Time отдельной задачи vs срок всего
бэклога vs стоимость**, а не как «дробление — всегда хорошо» — все три пути (не дробить,
дробить без доп. людей, дробить + нанять) валидны в зависимости от того, что команда
оптимизирует, интересно сравнить цифры разных команд именно по этим трём осям.

**Урок**: батчинг — это не односторонне «чем мельче, тем лучше» (в отличие от чистой Lean-теории
малых батчей). В *длинном* пайплайне с полом в 1 день на стадию дробление имеет реальную цену
(и в worker-days, и в календарном сроке всего бэклога), которую нужно окупать реальной
дополнительной capacity — поднятие одних только WIP-лимитов не помогает, если ограничение не
там. Плюс — второй заход к закону Литтла, уже вместе со стоимостью и с разницей между
«Lead Time одной задачи» и «срок всего бэклога».

## Бэклог идей на будущее (не откалиброваны, из первого обсуждения)

Остальные пункты исходного каталога — не вошли в первые 4 уровня, но стоит держать про запас:

- **Four-eyes / `requiresDifferentResource`** — код-ревью требует другого воркера, чем автор;
  при команде из 1-2 backend это создаёт скрытый затор, невидимый в списке навыков. Поле уже
  реализовано в движке, но ни разу не используется ни в одном пресете (см. [[roadmap]]) — будет
  первым сценарием, который его реально задействует.
- **Очередность без приоритетов** — в движке нет class-of-service, но порядок задач в списке =
  порядок pull. Сценарий: срочная мелкая задача закопана в хвосте бэклога за тремя долгими.
  Фикс — просто переупорядочить список вручную.
- **Стоимость как ограничение, а не просто побочная метрика** — разный `costPerDay`, задать
  явный бюджетный потолок и просить оптимизировать Lead Time *при* этом потолке.
- **Длинная ветвящаяся цепочка целиком** (полный `twork-process`, 19 стадий, вероятностные
  переходы Design Review/Automation) — смещающийся constraint: почини один затор, вылезет
  следующий. Хорошо заходит после того, как команды освоили Levels 1-4 по отдельности.
- **«Рельсы» / скилл-локап через `Task.RequiredSkills`** — намеренно использовать гочу с
  `requiredSkills` на задаче (см. раздел про механику движка) как фичу: задача жёстко привязана
  к одному навыку/ветке и голодает, если единственный подходящий воркер занят. Отдельный урок
  про то, что негибкая маршрутизация задач — тоже источник задержек.
- **Финальный «босс»** — комбинация нескольких поломок сразу (перекос состава + плохой WIP +
  плохая декомпозиция + long pipeline) на максимально кривом конфиге, для команд, прошедших
  все уровни по отдельности.

## Формат поставки

Отдельные JSON-файлы (`StartSimulationRequestDto`) в `training-scenarios/`, импортируются через
UI кнопкой «Импорт» — не трогают код/пресеты в `Factories/*`, не требуют пересборки:

- `training-scenarios/level-1-single-bottleneck.json`
- `training-scenarios/level-2-excess-qa.json`
- `training-scenarios/level-3-wip-chaos.json`
- `training-scenarios/level-4-decomposition-tax.json`
- `training-scenarios/README.md` — памятка фасилитатору: ожидаемый симптом, измеренный baseline
  по метрикам (`efficiencyPercent`, `flowEfficiency`, `leadTime.p50/p85`, `totalCost`), и
  ориентир «на что должны выйти команды после фикса» — чтобы можно было быстро отличить команду,
  которая реально поняла первопричину, от команды, которая просто накидала WIP-лимитов наугад.

## Как проверялись цифры

Все baseline-цифры в этом документе — не расчёт на бумаге, а реальные прогоны:
`dotnet run --project KanbanFlowApi`, затем `POST /api/simulation/start` с каждым файлом
(`daysToSimulate: 0` — до полного завершения бэклога) и `POST /api/simulation/all-metrics` на
полученном состоянии. Все 4 файла проходят валидацию и раскрываются без ошибок. При изменении
файлов сценариев эту проверку стоит повторить — некоторые эффекты (см. `flowEfficiency` в
Level 3) оказались контринтуитивны и разошлись с оценкой на бумаге до реального прогона.
