# Обучающие сценарии — памятка фасилитатору

4 конфига от простого к сложному. Каждый импортируется через UI (кнопка «Импорт») и не требует
пересборки приложения. Полное обоснование дизайна, почему выбраны именно эти числа и как они
были получены — в [`../training-scenarios.md`](../training-scenarios.md). Здесь — только то, что
нужно держать под рукой во время сессии.

**Правило игры для всех уровней**: общая длительность задач по каждому навыку — неизменна.
Всё остальное (состав команды, WIP-лимиты, дробление/слияние задач, структура workflow) —
можно менять свободно.

Все цифры ниже — реально измеренный baseline (seed=42, `useVariability: true`), не оценка на
бумаге. Диапазон "хорошо после фикса" — ориентир, не жёсткий порог; у разных команд он будет
чуть разным из-за случайности.

---

## Level 1 — `level-1-single-bottleneck.json`

**Урок**: найти ограничение, а не считать головы.

| Метрика | Baseline (как есть) |
|---|---|
| День завершения | 508 |
| `dev-be.efficiencyPercent` | 100 |
| `dev-fe` / `qa` `.efficiencyPercent` | **0 / 0** |
| `leadTime.p50` / `p85` | 32.0 / 67 |
| `flowEfficiency` | 14.7% |
| `totalCost` | 152400 |

**Что смотреть в первую очередь**: `dev-fe`/`qa` буквально ни разу не берут задачу за весь
прогон — команда из 3 человек, а работает один. Симптом виден без всяких метрик — просто по
доске (Todo не разгребается, Developing никогда не пустует).

**Ожидаемый фикс**: дать `dev-fe`/`qa` навык `backend` (сменить состав) — самый дешёвый и
явный путь. После фикса на 3 backend-способных людях день завершения должен упасть
кратно (примерно в 3 раза — измерено: 508 → 164).

**Ловушка для фасилитатора**: если команда вместо этого добавляет ещё workers с навыком backend
(нанимает 4-го/5-го), это тоже валидно — но дороже. Стоит спросить, почему не переиспользовали
уже имеющихся людей.

## Level 2 — `level-2-excess-qa.json`

**Урок**: мощность нужна там, где реальный спрос, а не «QA всегда мало».

| Метрика | Baseline |
|---|---|
| День завершения | 825 |
| `dev1.efficiencyPercent` | 99.5 |
| `qa1.efficiencyPercent` | 44.0 |
| `qa2` / `qa3` / `qa4` `.efficiencyPercent` | **0 / 0 / 0** |
| `leadTime.p50` / `p85` | 50.5 / 90.45 |
| `flowEfficiency` | 17.33% |
| `totalCost` | 412500 |

**Что смотреть**: 3 из 4 QA не берут вообще ни одной задачи за весь прогон — на CFD Developing
явно «толще» Testing. `totalCost` тоже показательна — 5 зарплат при факте, что 3 из них почти
целиком уходят в простой.

**Ожидаемый фикс**: перебалансировать состав — часть QA переквалифицировать в backend/frontend
(или честно сократить QA-часть команды). После разумного фикса `totalCost` должен заметно упасть
(меньше людей на скамейке запасных), день завершения — сократиться.

## Level 3 — `level-3-wip-chaos.json`

**Урок**: закон Литтла живьём + осторожно с `flowEfficiency`.

| Метрика | Baseline (WIP не ограничен) | После разумных WIP-лимитов* |
|---|---|---|
| День завершения | 358 | 357 |
| `leadTime.p50` / `p85` | 267.0 / 326.15 | **28.5 / 55.6** |
| `throughput.overall` | 0.223 | 0.224 (не изменился) |
| `flowEfficiency` | **100%** (!) | 29.04% |

\* контрольный прогон: `wipLimit=1` у воркеров + Todo=5/Developing=3/Testing=2.

**Важно — методическая ловушка**: `flowEfficiency` в baseline выглядит идеально (100%), хотя
это худший сценарий из всех четырёх по Lead Time. Причина — метрика считает только ожидание в
Buffer-стадиях; без стадийных WIP-лимитов ждать негде, всё сразу «в работе» (пусть и размазанной
`1/N` между несколькими задачами у одного воркера). **Ориентируйтесь на `leadTime.p50/p85` при
стабильном `throughput`, не на `flowEfficiency`** — она тут may fool you.

> ⚠️ **Про размер состояния**: этот сценарий — единственный из четырёх, где `wipLimit`
> воркеров сильно больше 1 (много активных назначений в день → по записи активности на каждое,
> см. `WorkProgressService.SimulateWorkDay`). При «Рассчитать до конца» итоговое состояние
> (конфиг+доска+вся история по дням) сохраняется в `localStorage` браузера — на 80 задачах и
> `wipLimit=48` это ≈5.8 МБ, у некоторых браузеров (особенно Safari) это близко к пределу
> квоты. Если всё равно не влезает — дальше можно снижать `wipLimit` (см. таблицу ниже), но
> это постепенно смазывает саму иллюзию `flowEfficiency≈100%`, ради которой уровень задуман.
>
> | `wipLimit` | День | `flowEfficiency` | Размер состояния |
> |---|---|---|---|
> | 48 (текущий) | 358 | 100% | ~5.85 МБ |
> | 30 | 426 | 87.0% | ~4.79 МБ |
> | 24 | 367 | 75.8% | ~3.98 МБ |
> | 18 | 352 | 63.6% | ~3.25 МБ |
>
> `wipLimit=48` подобран так, чтобы совокупная capacity команды (2×48+48=144) превышала объём
> задач (80) с тем же запасом (×1.8), что и в исходном дизайне на 10 задачах (2×6+6=18).

**Что смотреть**: у `dev1`/`dev2` сразу по несколько активных назначений одновременно с первого
дня — это видно в `assignedAssignments` на доске.

**Ожидаемый фикс**: снизить `wipLimit` воркеров до 1, добавить стадийные WIP-лимиты под реальную
capacity. `throughput` почти не изменится — это ожидаемо и это часть урока (не «фикс поднял
пропускную способность», а «тот же объём работы стал доезжать быстрее»).

## Level 4 — `level-4-decomposition-tax.json`

**Урок**: дробление задач — не односторонне полезно; есть налог на округление по стадиям +
разница между «Lead Time одной задачи» и «сроком всего бэклога».

| Метрика | Baseline (40×L) | Просто дробим (160×S) | + WIP на Dev/CR/Testing | + WIP + 5-й воркер |
|---|---|---|---|---|
| День завершения | 472 | 600 (хуже) | 600 (без изменений) | **402** (лучше) |
| `leadTime.p50` / `p85` | 97.0 / 113.15 | **32.0 / 35.15** (лучше) | без изменений | **25.0 / 28** |
| `throughput.overall` | 0.0847 | 0.267 | без изменений | 0.398 |
| `totalCost` | 188800 | 240000 (+27%) | 240000 | 201000 (+6.5%) |

**Что смотреть**: это открытый эксперимент, не сценарий с одним правильным ответом. Дайте
команде раздробить L-задачи на S (нужно сохранить суммарную длительность по навыку —
1×L ≈ 4×S по номиналу) и явно спросите, что именно они оптимизируют: Lead Time одной задачи,
дату сдачи всего бэклога, или стоимость. Три этих оси двигаются по-разному.

**Ловушка**: поднятие только стадийных WIP-лимитов (Developing/Code Review/Testing) без
добавления человека **не даёт вообще никакого эффекта** в этом конфиге — реальное ограничение
не там (у каждого воркера персональный `wipLimit=1`, backend-людей всего двое). Если команда
крутит WIP-лимиты и не видит изменений — это сигнал проверить, не сидит ли ограничение уровнем
ниже (capacity конкретных людей), а не в стадийном лимите.

**Хороший результат**: дробление + расширение состава (пусть даже на одного человека) даёт
выигрыш и по Lead Time, и по сроку всего бэклога, при умеренном росте стоимости (~+6.5%, не
+27%, как при дроблении без усиления команды).
