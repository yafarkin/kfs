## Frontend: инфраструктура

- **Нет сборки/бандлера вообще.** Голые `<script src="app.js?v=45">` с ручным номером версии
  для сброса кэша браузера. Забыть/перепутать номер — системная проблема, не разовая ошибка

  (esbuild/vite, без фреймворка) убрал бы весь этот класс проблем и заодно дал бы модули вместо
  текущей схемы "всё — глобальные функции и две глобальные переменные (`configTemplate`,
  `simulationState`), которые дёргают друг друга по имени".
- ~1860 строк встроенного `<style>` внутри `index.html` — стоит вынести в отдельный CSS-файл
  при следующей серьёзной правке стилей.
- ✅ Забытые ключи localStorage разведены: `STORAGE_KEYS` теперь только актуальные
  (`CONFIG_TEMPLATE`, `SIMULATION`), а легаси-ключи прошлых версий вынесены в
  `LEGACY_STORAGE_KEYS` с комментарием — `clearAllLocalStorage()` их всё ещё чистит у тех,
  у кого остались, но новых записей по ним нет.
- ✅ **Баг (исправлено)**: `saveSimulationToStorage()` не ловила `QuotaExceededError` от
  `localStorage.setItem` — на длинных прогонах с высоким `wipLimit` (много активных назначений
  в день → по записи активности на каждое, см. `WorkProgressService.SimulateWorkDay`) итоговое
  состояние легко превышает квоту `localStorage` (~5-10 МБ). Конкретный триггер: Level 3
  training-scenario после ×10-масштабирования задач и подъёма `wipLimit` до 60 даёт ~10 МБ
  состояния за 448 дней. Ошибка вылетала прямо из `startSimulation()` **до** `renderBoard()`/
  `calculateAllMetrics()` — пользователь вместо готового результата видел «Ошибка запуска: The
  quota has been exceeded», хотя симуляция на бэкенде отработала полностью корректно. Теперь
  `saveSimulationToStorage()` ловит ошибку сама и показывает отдельный тост («результат слишком
  большой для сохранения, но работает в этой вкладке»), не блокируя рендер/метрики.
  **Ирония**: при первом деплое фикса забыл поднять `app.js?v=NN` в `index.html` — ровно тот
  системный класс проблем с ручным кэш-бастером, что уже описан пунктом выше. Пользователь
  какое-то время видел старое (незачиненное) поведение из закэшированного `app.js`. Level 3
  дополнительно сокращён на 20% задач (100→80, `wipLimit` пересчитан 60→48) — снижает шанс
  вообще упереться в квоту, а не просто ловит её постфактум (см. `docs/training-scenarios.md`).
  **Смежное, не исправлено**: `renderHistory()` рендерит всю историю одним `innerHTML` без
  пагинации — на таких объёмах (10k+ записей активности) может давать заметный лаг рендера,
  хоть и не блокирует работу, как было с квотой.

- `.github/workflows/build.yml` делает только `restore → build → test` — нет lint/format:

  types are up to date** генерирует `api-types.d.ts` из схемы и падает на рассинхроне
  (см. раздел DTO и `docs/api-contract.md`).

## Архитектура (не проблема, просто ограничение на будущее)

- Бэкенд полностью stateless по дизайну — всё состояние живёт в localStorage браузера
  (`SimulationController`/`ProcessEditorController`/`WorkerEditorController` явно
  документируют это в докстрингах). Это осознанное и оправданное решение для текущего
  масштаба проекта, не баг. Упомянуто только потому, что ограничивает будущие фичи вроде
  "поделиться конфигом с коллегой" или многопользовательского режима — это будет полноценная
  новая подсистема (персистентность на сервере), а не апгрейд существующей.
