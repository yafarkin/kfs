# TODO / технический долг

Список наблюдений по бэкенду и фронтенду (движок симуляции, DTO, тесты, UI) после
нескольких раундов ревью. Ничего из этого не блокирует работу — фиксируем, чтобы не забыть.
Обновлено после раунда: DTO-рефакторинг (слияние StartSimulationRequestDto/
ApiSimulationConfigDto, пресетов) + сквозные тесты + анимация доски.

## Тесты

### Сделано
- Добавлен `EndToEndSimulationTests.cs` — первые тесты, которые реально гоняют
  `SimulationController` (а не имитируют его логику), с полным DTO↔domain roundtrip через
  `ApiMapper` на каждом дне и проверкой метрик после полного прогона. Закрывает часть дыр
  ниже, но не все.

### Осталось
- **Нет тестов на уровне настоящего HTTP.** Все 184+ теста (включая новые
  `EndToEndSimulationTests`) вызывают C#-классы/контроллер напрямую в процессе — ни один не
  поднимает `WebApplicationFactory` и не бьёт по `/api/...` через настоящий JSON-биндинг
  ASP.NET. Баги сериализации на границе запрос↔DTO (например, отсутствующее поле в JSON,
  неправильный `[FromBody]`) такие тесты в принципе не поймают.
- **Нет браузерных E2E-тестов в CI** (Playwright/Cypress). Весь визуальный слой — доска,
  редактор конфигурации, анимация перемещения карточек — не защищён от регрессий ничем, кроме
  ручной проверки по запросу. За этот проект уже несколько раз баг находился только руками в
  браузере (маппинг скиллов, потеря `costPerDay`/`createsValue`, блокирующий `alert()`).
- Основная масса юнит-тестов по-прежнему конструирует состояние руками
  (`new BoardWorker { Assignments = [...] }`), минуя реальный путь, которым это состояние
  возникает в `TaskMovementService`/`WorkProgressService`. Годится для проверки формул, но
  плохо ловит интеграционные баги — как и раньше, это не критично, раз есть
  `EndToEndSimulationTests`.

## DTO

### Сделано
- `StartSimulationRequestDto` теперь наследуется от `ApiSimulationConfigDto` вместо
  дублирования тех же 5 полей — JSON-контракт не изменился (System.Text.Json сериализует
  унаследованные свойства в тот же плоский объект). Дублирующая перегрузка
  `ApiMapper.ToDomainConfig(StartSimulationRequestDto)` убрана.
- `ConfigPresetDto` и `TaskPresetDto` удалены как мёртвый код (нигде не использовались).
- `ProcessPresetDto`/`WorkerPoolPresetDto` теперь наследуются от общего `PresetDto`
  (Name/DisplayName/Description/IsDefault) вместо дублирования этой четвёрки в каждом.
- На фронте `configTemplate.workflow.transitions` (был отдельным плоским списком) переведён
  на тот же вложенный формат, что и backend API (`stage.transitions`) — убраны
  `buildWorkflowForBackend()`/`flattenStageTransitions()`, конвертеры туда-обратно, которые
  дважды становились источником багов потери данных.

### Осталось
- **`ApiBoardWorkerDto` хранит назначения дважды**: и `AssignedTaskKeys` (список строк), и
  `AssignedAssignments` (полные объекты). `ApiMapper.ToDomainBoard` держит ветку "если есть
  новый формат — используем его, иначе старый" (легаси-фолбэк на случай старых экспортов).
  Кандидат на удаление `AssignedTaskKeys` и старой ветки, если обратная совместимость со
  старыми JSON-экспортами не важна.
- **Нет контракта между C#-DTO и JS.** Формат JSON нигде не зафиксирован, кроме как "читай
  C#-класс и угадывай" — именно отсюда взялись все три бага этого проекта на границе
  бэкенд/фронт (`costPerDay`, `createsValue`, формат `transitions`). Swagger/OpenAPI уже
  подключён (`AddSwaggerGen` в `Program.cs`), но следующего шага — генерации TS/JSDoc-типов
  для фронта из OpenAPI-схемы — нет. С ним такие рассинхроны ловились бы на этапе разработки.

## Движок (TaskMovementService / SimulationValidationService)

- Мёртвый код в `TaskMovementService`: `GetRequiredSkillsForStage`, `HasAllRequiredSkills`
  (строки ~548, ~564) — нигде не вызываются, можно удалить.
- `SimulationValidationService.ValidateCanContinue` — самый мутный метод в движке, несколько
  почти дублирующих друг друга проверок "можно ли продолжать". Работает, но при следующем
  touch стоит упростить.
- `TaskMovementService` (~690 строк) многовато на один класс: поиск/назначение воркера,
  топология графа стадий и вероятностные переходы можно разнести на 2 класса.
- **Новая находка**: `simulateDay()` в `app.js` (~строка 370) на каждый день перезаписывает
  `simulationState.config.useVariability` из текущего состояния UI-тумблера. Если пользователь
  переключит "Вариативность" посреди уже идущей симуляции, режим детерминизма тихо меняется
  для последующих дней, и предыдущие дни (в одном режиме) смешиваются с последующими (в
  другом) в рамках одного прогона — подрывает воспроизводимость через `seed`+
  `RandomCallCount`, ради которой это всё затевалось. Стоит либо блокировать смену
  вариативности после старта симуляции, либо явно предупреждать пользователя, что это повлияет
  только на будущие дни.

## Frontend: инфраструктура

- **Нет сборки/бандлера вообще.** Голые `<script src="app.js?v=45">` с ручным номером версии
  для сброса кэша браузера. Забыть/перепутать номер — системная проблема, не разовая ошибка
  (за один только этот проект номер бампался руками несколько раз). Даже минимальный бандлер
  (esbuild/vite, без фреймворка) убрал бы весь этот класс проблем и заодно дал бы модули вместо
  текущей схемы "всё — глобальные функции и две глобальные переменные (`configTemplate`,
  `simulationState`), которые дёргают друг друга по имени".
- ~1860 строк встроенного `<style>` внутри `index.html` — стоит вынести в отдельный CSS-файл
  при следующей серьёзной правке стилей.
- Забытые ключи localStorage в `clearAllLocalStorage()` (`kanbanflow_worker_editor`,
  `kanbanflow_process_presets`, `kanbanflow_worker_presets`) — код, который их писал, давно
  удалён. Не вредят, но стоит либо убрать, либо задокументировать, зачем оставлены.

## CI / качество кода

- `.github/workflows/build.yml` делает только `restore → build → test` — нет lint/format:
  ни ESLint/Prettier для JS, ни `dotnet format --verify-no-changes` для C#.
- `<Nullable>enable</Nullable>` включён в обоих csproj, но без `TreatWarningsAsErrors` —
  предупреждения о nullability могут молча накапливаться.
- Swagger/OpenAPI уже подключены (см. раздел DTO выше) — можно опереться на это для
  контрактных проверок фронт/бэк, а не только для документации.

## Архитектура (не проблема, просто ограничение на будущее)

- Бэкенд полностью stateless по дизайну — всё состояние живёт в localStorage браузера
  (`SimulationController`/`ProcessEditorController`/`WorkerEditorController` явно
  документируют это в докстрингах). Это осознанное и оправданное решение для текущего
  масштаба проекта, не баг. Упомянуто только потому, что ограничивает будущие фичи вроде
  "поделиться конфигом с коллегой" или многопользовательского режима — это будет полноценная
  новая подсистема (персистентность на сервере), а не апгрейд существующей.

## Продуктовые фичи — черновик (результаты тренировочной сессии с командой)

> ⚠️ **Черновой вариант.** Это сырые результаты прогона тренировочной сессии с командой.
> Каждый пункт нужно прорабатывать отдельно (дизайн, механика, влияние на движок/метрики),
> прежде чем брать в работу. Здесь только фиксируем идеи, чтобы не забыть.

1. **Намного больше задач во всех кейсах** — текущих объёмов задач не хватает для наглядной
   демонстрации потока; нужно увеличить количество задач во всех пресетах/кейсах.
2. ✅ **Ввести "грейды" воркера** — реализовано как quick-fill в редакторе команд: пресеты
   роль×грейд (`backend/frontend/qa` × `стажёр..лид`, `WorkerGradePresetsFactory`,
   `GET /api/editor/workers/grade-presets`) одноразово заполняют Performance/Отклонения/
   CostPerDay, поля остаются редактируемыми вручную. Стажёр/джун намеренно сделаны
   медленнее и дороже за единицу производительности, чем миддл (+нестабильнее по срокам),
   чтобы наём джунов не был читерски выгодной стратегией.
3. ✅ **Показывать общую длительность задач** — в редакторе задач над списком выводится
   `N задач · min–max дней суммарно` (сумма диапазонов T-Shirt размеров, без учёта
   воркеров/стадий — оценочная метрика для контроля нарезки). Попутно исправлен баг:
   `TShirtType.XL` был объявлен в UI/DTO, но отсутствовал в самом enum и в
   `GetDaysToComplete` — XL-задачи молча считались как XS везде, включая саму симуляцию.
   Добавлен `XL` в enum, диапазон 16–30 дней.
4. ✅ **Кнопка "склонировать" для воркера** — в карточке воркера кнопка рядом с
   "Выше/Ниже/Удалить" (`cloneWorker`). Копирует все поля кроме логина (уникальный логин
   вида `login-copy`, `login-copy-2`, ...), клон вставляется сразу после оригинала.
5. **Разбиение/склейка задач одной кнопкой** — продумать UX-механику, чтобы одна кнопка
   позволяла и разбивать задачу на части, и склеивать задачи обратно.
