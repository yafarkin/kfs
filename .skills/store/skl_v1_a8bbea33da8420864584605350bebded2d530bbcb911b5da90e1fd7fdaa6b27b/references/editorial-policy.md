# Russian editorial policy

This file is intentionally written in Russian — it describes how to write Russian documentation. Always consult it before editing or producing any Russian text.

## Терминология

Используйте корректные варианты написания. Левый столбец — частые ошибки, правый — правильное написание.

| Неправильно                  | Правильно             |
|------------------------------|-----------------------|
| Кеш, кеширование             | Кэш, кэширование      |
| Хэш, хэширование             | Хеш, хеширование      |
| Бекап                        | Бэкап                 |
| Файрвол                      | Фаервол               |
| Бекенд, бэкэнд, бекэнд       | Бэкенд                |
| Ендпоинт, эндпойнт           | Эндпоинт              |
| Залогиньтесь                 | Авторизуйтесь         |
| Перцентиль, персентиль       | Процентиль            |
| Кластера (мн. число)         | Кластеры              |

## Оформление

* **Якоря** — к каждому подзаголовку `##` и `###` добавляйте якорь на английском в kebab-case: `## Создать кластер {#create-cluster}`.
* **Числительные** — пишите цифрами. К количественным числительным наращение не приписывается: «5 лет», а не «5-ти лет». К порядковым — через дефис: `5-й запуск`, `10-го числа`.
* **Элементы интерфейса** — выделяйте жирным, без кавычек и без слова «кнопка»: нажмите **Сохранить**.
* **Вводимые термины** — курсивом: _термин_ — определение.
* **Технические имена** (переменные, методы, конфиги, имена бинов, кэшей, jobs, топиков, команд) — в обратных апострофах: `statisticsOverviewCache`, `ManagedAdStatusOutboxJob`.
* **Названия продуктов, технологий, протоколов** — без апострофов и кавычек: Spring Boot, Kafka, gRPC, PostgreSQL.
* **Код и консольные команды**, занимающие строку целиком, — выносите в блок кода. Команду и её вывод размещайте в разных блоках.
* **Тире** `—` вместо дефиса `-` в предложениях: «значение — число», а не «значение - число».
* **Ссылки** — встраивайте в текст. Никогда не используйте «тут», «здесь», «сюда», «по адресу».
    * Плохо: читайте [тут](...).
    * Хорошо: смотрите [как создать бакет](...).
* **Навигация по UI** — через символ стрелки →: Настройки → Безопасность.
* **Заголовки и подзаголовки** — без точки в конце.
* **Ячейки таблиц** — без точки в конце.
* **Эмодзи** — не использовать в тексте документации.
* **Инфоплашки** — допустимые комбинации: `:::info Примечание`, `:::info В разработке`, `:::tip Совет`, `:::caution Важно`, `:::danger Внимание`. Любые другие приводите к разрешённым.
* **Пустые строки** — между списком и текстом, до и после подзаголовка.

## Списки

Правила выбора и оформления списка зависят от смысла:

* Порядок не важен → маркированный список со звёздочкой `*`.
* Порядок важен → нумерованный список.
* Если в каждом элементе есть глагол → каждый элемент с большой буквы, точка в конце.
* Если элементы — ссылки → без знаков препинания в конце.
* Если перед списком есть вводная фраза с двоеточием и в элементах нет активного глагола → элементы с маленькой буквы, в конце точка с запятой, последний — точка.
* Если перед списком вводная фраза с двоеточием и элементы из 1–2 слов без пунктуации → с маленькой буквы, через запятую.
* Каждый элемент нумерованного списка — с большой буквы, точка в конце.
* Вложенный список — отступ 4 пробела.

## Стилистика

* Обращайтесь к читателю на «вы» (с маленькой буквы) в повелительном наклонении: «заполните поле».
* Одно предложение — одна мысль. Сложносочинённые разбивайте на простые.
* Активный залог вместо страдательного: «сервис публикует событие», а не «событие публикуется сервисом».
* Глагол вместо отглагольного существительного: «чтобы создать», а не «для создания».
* Сначала где, потом что: «в правом верхнем углу нажмите **Сохранить**».
* Убирайте «можно» и «нужно», если модальность не нужна по смыслу: «нажмите **Сохранить**», а не «нужно нажать». Если действие действительно опционально — «вы можете».
* Никаких скобочных уточнений — выносите в отдельное предложение, выделяйте запятыми или удаляйте. Скобки допустимы только для расшифровки сокращений и перечисления синонимов.
* Причастный оборот ставьте перед определяемым словом.
* Никаких слов-паразитов: «чтобы», а не «для того чтобы».
* Тон нейтральный и дружелюбный. Не обвиняйте пользователя: «если токен утерян», а не «если вы потеряли токен».

## Баланс технической глубины

Документация в `docs/domain/` должна быть читаема для аналитиков, QA и бизнес-стейкхолдеров, но разработчик должен иметь возможность найти grep'ом любое имя джобы, топика или эндпоинта и попасть на нужную страницу.

**Не убирайте технические маркеры ради читаемости — вместо этого добавляйте вокруг них пояснения.**

## Что проверять при ревью каждого абзаца

1. Орфография, грамматика, пунктуация.
2. Терминология из таблицы выше.
3. Правила оформления: тире, ссылки, технические имена, элементы UI.
4. Правила списков.
5. Стилистика: активный залог, отсутствие отглагольных существительных, обращение на «вы».
6. Сохранность технических маркеров.
