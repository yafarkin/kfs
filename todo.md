## Тесты: зелёные, но пропускают реальные баги

Оба недавних багфикса (`bb3e240` — воркер не освобождался после завершения
задачи, `03dc70c` — маппинг скиллов воркера) были найдены руками, а не

**после** фикса, а не находили баг заранее. Причина видна по структуре
`KanbanFlow.Tests`:

- Почти все тесты — модульные и **конструируют состояние руками**
  (`new BoardWorker { Assignments = [...] }`), минуя реальный путь, которым
  это состояние возникает в `TaskMovementService`/`WorkProgressService`.
  Так легко проверить формулу, но легко и не заметить, что настоящий код
  никогда не проведёт объект в такое состояние (или наоборот — заведёт его
  туда, где тест этого не ожидает).
- **Нет ни одного теста, который гоняет `SimulationController` напрямую**
  (`grep -rl SimulationController KanbanFlow.Tests` — пусто). Бага в
  `ApiMapper` (маппинг скиллов) это касалось напрямую: сериализация/
  восстановление состояния между HTTP-вызовами — ровно то место, которое не
  покрыто ничем, кроме точечных тестов на сам маппер.
- Мало **многодневных прогонов** через реальный цикл дня
  (`StartNewDay → ProcessMovements → SimulateWorkDay → ProcessMovements`,
  как в контроллере) — большинство тестов проверяют один вызов сервиса, а
  не накопление состояния день за днём, где и жил баг с WIP-лимитом.

**Не чиню сейчас** (по просьбе). Если возвращаться к этому — самый дешёвый
следующий шаг: 1-2 сквозных теста, которые гоняют `StartSimulation` с

## DTO

Разделение API DTO (`KanbanFlowApi/Dtos`, ~1085 строк) и доменных моделей
(`KanbanFlowSerivce/Dtos`, ~777 строк) **уже есть и оправдано** — это не
копипаста: API DTO плоские (ссылки на воркера/стадию — это `string`, а не
объект), потому что домену нужны кольцевые ссылки (`BoardStage.PrevStages`/
`NextStages`, `BoardTask.CurrentStage`), а JSON их не терпит. Явный маппер
`ApiMapper.cs` (556 строк) существует именно для этого — разворачивает граф
стадий по именам в обе стороны. Так что просьба "чтобы точно было
разделение" уже выполнена, это не нужно строить с нуля.

Что реально смущает:

- **Объём**: 26 файлов DTO + 556-строчный ручной маппер означает, что любое
  новое поле в домене трогается в 3 местах (domain → DTO → mapper в обе
  стороны). Риск не в дизайне, а в поддержке — легко забыть прокинуть поле в
  одну из сторон (собственно, `03dc70c` — это ровно такой случай).
- **Дублирование "пресетных" DTO**: `ConfigPresetDto`, `ProcessPresetDto`,
  `TaskPresetDto`, `WorkerPoolPresetDto` — у всех четырёх одинаковый костяк
  (`Name`, `DisplayName`, `Description`, `IsDefault`) и отличается только
  одно поле с payload'ом. Кандидат на общий базовый record, но не критично.
- Стоит рассмотреть генерацию мапперов (Mapster/Mapperly) хотя бы для
  однотипных кусков, чтобы убрать часть ручного кода — но это не горит, раз
  логика мест с реальными графами всё равно останется ручной.
